# Интерактивный онбординг

Кампания `intro_v1` выключена по умолчанию. `INTERACTIVE_ONBOARDING_ENABLED=1` одновременно включает регистрацию новых участников и обработку очереди. Участие создаётся только при первой вставке пользователя из личного `/start`. Администратор, боты и пользователи с исторической отметкой отправки исключены. Старые сообщения сохраняют рабочие кнопки.

День 1 — дата первого `/start` в Москве. Его три сообщения отсчитываются от момента регистрации. Остальные привязаны к московскому календарю. Все задания имеют окно актуальности **5 минут** с момента `due_at`. Планировщик проверяет очередь каждые 5 секунд и помечает просроченные задания `expired`. Пяти минут достаточно для короткого сбоя и меньше минимального интервала между шагами. После длительного простоя пропущенные шаги не догоняются.

Захват фиксируется в PostgreSQL до вызова Telegram. Состояния `sent`, `failed`, `expired` и `uncertain` исключены из очереди. При явном ограничении Telegram по частоте отправка может повториться после указанной паузы внутри окна актуальности. Таймаут, обрыв связи, остановка после захвата или сбой записи результата могут оставить неизвестный исход. Такие попытки не повторяются автоматически. Поэтому авария иногда приводит к пропуску шага. Не возвращайте `uncertain` в очередь вручную без достоверной проверки исхода.

## Локальная проверка

Установите зависимости из `requirements.txt`. На Windows с отсутствующей базой часовых поясов потребуется `tzdata`.

```sh
python -m unittest discover -s tests -v
```

Для интеграционных тестов задайте `ONBOARDING_LOCAL_TEST_DSN` на выделенную временную локальную БД. Тесты создают и удаляют собственные схемы. Telegram и ЮKassa подменяются заглушками. Mini Apps сохраняют существующий запуск из обычной клавиатуры и существующий адрес. Для проверки открытия, возврата и сохранения отметок на клиентах Telegram используйте отдельного тестового бота.

## Webhook ЮKassa

Webhook использует существующие идентификатор магазина и `YOOKASSA_SECRET_KEY` для запроса платежа к API ЮKassa. При настроенном `YOOKASSA_WEBHOOK_SECRET` он также проверяет заголовок уведомления. Недоступность API или PostgreSQL возвращает 503, чтобы ЮKassa могла повторить доставку. Успешный донат проходит проверку API и завершается без изменений в базе. Для подписки запись идентификатора платежа, продление и реферальный бонус фиксируются одной транзакцией.

Выполняйте переключение webhook без пересечения старого и нового обработчиков. До переключения сверяйте подтверждённые подписочные платежи с уже выданными начислениями. На время смены версии приостановите обработку старым webhook с ответом 503, затем примените `migrations/002_yookassa_webhook.sql` и включите новый обработчик. Миграция один раз фиксирует границу по времени подтверждения оплаты. Новый обработчик принимает ранее созданные платежи, подтверждённые начиная с этой границы. Платежи, подтверждённые раньше, требуют сверки перед любым ручным начислением. Это защищает от повторной обработки исторических уведомлений, для которых раньше не сохранялся идентификатор платежа.

При откате онбординга используйте сборку с проверкой через API и сохраняйте обе таблицы ЮKassa. Возвращать старый webhook с обработкой данных из тела уведомления нельзя.

## Применение после разрешения на запуск

1. Сверьте активный коммит, число реплик, ключ `users.user_id` и охват исторических пользователей. Убедитесь, что все прежние пользователи присутствуют в `users` либо имеют историческую отметку в `onboarding_messages`. Сверьте существующий резервный снимок и агрегаты исторических отправок. Проверьте процедуру на тестовой базе.
2. Примените `migrations/001_interactive_onboarding.sql` к нужной БД через `psql -X -v ON_ERROR_STOP=1 -f migrations/001_interactive_onboarding.sql` из авторизованного сеанса. Примените вторую миграцию при переключении webhook по инструкции выше. Проверьте появление таблиц и индексов в нужной схеме и права роли приложения на чтение и запись новых таблиц.
3. Разверните версию с выключенной кампанией. Убедитесь, что прежние реплики остановлены и старые планировщики больше не выполняются. Пользователи, зарегистрированные в промежутке до включения кампании, не попадут в неё задним числом.
4. Включите `INTERACTIVE_ONBOARDING_ENABLED=1`. Проверьте агрегаты по `campaign_version`, `step_key` и `status`, а также ошибки планировщика. На новых шагах не должно появляться более одной успешной доставки на ключ.

## Откат

Уберите флаг или задайте `INTERACTIVE_ONBOARDING_ENABLED=0` и дождитесь остановки всех процессов с включённым флагом. Сохраните обе таблицы, чтобы при повторном включении помнить уже выполненные отправки. Используйте для отката сборку с выключенными прежними планировщиками. Не откатывайте схему удалением таблиц и не возвращайте старую рассылку автоматически.
